# DJ-001 — PostgreSQL/Redis Django baseline

Date: 2026-10-24

## Outcome

PASS. The local Docker Compose stack was built and brought up without removing
volumes. PostgreSQL, Redis, Django API, and Celery worker all reached their
configured healthy state. PostgreSQL is the database used for checks and tests;
the PostgreSQL-marked concurrent ticket-claim test executed and passed.

## Changes

- Corrected ASGI initialization ordering in `config/asgi.py`. Django now builds
  its ASGI application before websocket routing imports ORM-backed consumers.
  This fixed the API's Compose startup failure (`AppRegistryNotReady`).
- Added a fresh-process ASGI import regression test.
- Closed database connections opened by claim-test worker threads so PostgreSQL
  test database teardown is clean.
- Kept `db`, `redis`, and `worker` only on the internal `backend` network.
  Added the non-internal `edge` network to `api` so its declared host port
  `8000` is actually reachable. PostgreSQL and Redis have no published ports.
- Updated README boot instructions to use Compose's wait mode and document the
  API edge/private-backend network boundary.
- Verified the existing liveness/readiness endpoints and their test coverage.
  Liveness is dependency-free; readiness checks PostgreSQL and Redis.

## Commands executed and results

```bash
docker compose config --quiet
docker compose up --build -d --wait --wait-timeout 90
docker compose ps --all
```

Result: all four services healthy. API was published as
`0.0.0.0:8000->8000/tcp`; PostgreSQL and Redis showed only their internal
container ports. The running versions reported by the containers were
PostgreSQL `16.15` and Redis `7.4.11`.

```bash
docker compose exec -T api python manage.py check --database default
docker compose exec -T api python manage.py makemigrations --check --dry-run
docker compose exec -T api python manage.py migrate --check
```

Result: system check passed with no issues; no model drift; migration check
passed (no output is Django's success behavior).

```bash
docker compose exec -T api pytest -m postgres \
  tests/test_core.py::test_parallel_claim_has_one_winner
docker compose exec -T api pytest
```

Result: PostgreSQL claim test passed (`1 passed`, not skipped); complete suite
passed (`11 passed`).

```bash
curl --fail --silent --show-error http://127.0.0.1:8000/api/health/ready/
```

Result: `{"status":"ok","checks":{"database":"ok","redis":"ok"}}`.

A reversible dependency-loss check was also run:

```bash
docker compose stop redis
# from the API container: GET /api/health/live/ and /api/health/ready/
docker compose start redis
docker compose up -d --wait --wait-timeout 90
```

Result while Redis was stopped: liveness returned `200 {"status":"ok"}`;
readiness returned `503` with database `ok` and Redis `unavailable`. The stack
was then restored and all services returned healthy. No
`docker compose down -v` command was run.

## Remaining gaps

- This is local Compose validation only; browser, load, deployment, and
  production-service validation were not run.
- Redis logged its standard host-level `vm.overcommit_memory` warning. It did
  not prevent health checks or tests, but a production host should apply the
  Redis-recommended kernel setting.

## Security notes

- No private projects, production services, secrets, or customer data were
  accessed. The Compose database and Redis use fictional local development
  credentials.
- PostgreSQL and Redis have no host-port mappings and are isolated on the
  internal Compose backend network. Only the API is published on port 8000,
  distinct from the concurrently running .NET stack's port 5000.
- The checked-in development secret/password defaults are not suitable for any
  non-local deployment. Use environment-provided unique secrets outside local
  development.
