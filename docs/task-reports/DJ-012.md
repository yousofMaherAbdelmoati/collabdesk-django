# DJ-012 — Django reporting and caching benchmark

## Status

PASS. Deterministic, append-only local fixture generation and opt-in reporting benchmarks were implemented and exercised at 10k, 50k, and 100k tickets against the local Compose PostgreSQL service.

## Changes

- Added `apps/reports/benchmarking.py` with deterministic generators for exactly 10,000, 50,000, or 100,000 fictional tickets. Fixtures use a caller-supplied namespace, a fixed PRNG seed, fixed 2024 UTC timestamps, and deterministic response-message UUIDs.
- Added `seed_benchmark_tickets`. It requires `--confirm-fictional-data`, is disabled outside local/dev/test settings, appends only tagged fixture data, creates no usable credentials, and is idempotent for a clean namespace.
- Added `benchmark_reporting`. It seeds/reuses the namespace, materializes one `ReportJob.result`, warms both paths, then compares `compute_report` live aggregation to cache-aside retrieval of that precomputed result. It records individual samples, p50/p95/p99/min/max latency, query counts, cache hit/miss counts, CPU deltas, RSS, and runtime/container configuration in JSON.
- The benchmark can use the configured cache or an explicit local-memory cache. The executed runs use `--cache-backend locmem` so the cache is isolated and repeatable; this is not a Redis benchmark.
- The seeder rejects duplicate tagged titles, preventing a run from reporting an ambiguous dataset.

## Remaining gaps

- No Redis benchmark was run. The measured cache is Django `LocMemCache`, intentionally selected for an isolated, reproducible local cache hit/miss run. Redis, browser, load, and production-service claims are not made.
- An earlier timed-out, one-off 100k attempt left 177,000 tagged fictional tickets under namespace `dj012-postgres-100k`. It was not deleted because this task must not destructively reset data. The validated 100k result uses the distinct `dj012-postgres-100k-final` namespace and was verified to contain exactly 100,000 distinct tagged titles.

## Security notes

- Commands only run when `DJANGO_ENV` is development/dev/local/test and require an explicit fictional-data acknowledgement.
- Fixtures are clearly tagged fictional, use unusable passwords, avoid customer content, and do not contact external or production services.
- The report records no connection strings, credentials, request bodies, or real-user data. Only platform/runtime metadata and aggregate benchmark measurements are stored.
