# DJ-002 — Django authentication and authorization

## Result

PASS. Authentication/authorization acceptance coverage was exercised in both the local SQLite fallback and a fresh local Compose API image backed by PostgreSQL and Redis.

## Changes

- Added session login/logout and a CSRF bootstrap endpoint under `/api/auth/`.
  Session cookies are HttpOnly and SameSite=Lax, use Secure outside development,
  and unsafe session requests remain CSRF-protected.
- Added short-lived Bearer API credentials with SHA-256-only storage, expiry,
  per-token revocation on logout, and no plaintext persistence.
- Added a database-backed, privacy-preserving per-address login rate budget.
- Defined role policy: customers create/access their tickets; agents claim open
  tickets and access only assigned conversations; application admins access all
  conversations. `role=admin` sets `is_staff`; only explicit superusers retain
  `is_superuser`.
- Replaced query-string WebSocket token handling with Django session-cookie
  authentication. Exact origin validation is required, and sessions are
  reloaded before socket events so server-side logout/expiry revokes an open
  connection.
- Added explicit credentialed CORS middleware with exact allow-lists, no
  wildcard, CORS/CSRF origin consistency validation, and rejection of unsafe
  requests from untrusted origins.
- Added the gated `seed_local_accounts` command. It requires an explicit
  password and only operates in development/dev/local/test, never
  production-like environments.
- Added `ExpiringToken` and `LoginRateLimit` migration, auth tests, and README
  operational/security documentation. The migration also normalizes existing
  user role/staff/superuser combinations to the new least-privilege policy.

## Remaining gaps

No task-scope implementation gaps found. A real browser, external reverse
proxy/TLS configuration, load testing, and a production deployment were not
performed or claimed. Production operators must provide a strong
`DJANGO_SECRET_KEY`, TLS, and exact CORS/CSRF/WebSocket origin values.

## Security notes

- Browser credentials are not accepted in WebSocket URLs, preventing token
  leakage through URL logs/history.
- Bearer token plaintext is returned only when issued and is never stored.
- Demo accounts are fictional, use a caller-supplied password, and are
  disabled outside explicitly local/test environments.
- CORS is not treated as authorization; session-authenticated unsafe actions
  retain CSRF checks and untrusted origins are rejected before reaching views.
