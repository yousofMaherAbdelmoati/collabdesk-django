# DJ-004 — Complete Django Channels chat protocol

## Result

PASS. The authenticated chat protocol was verified with its new ASGI
integration tests on local SQLite and on the repository's local Compose
PostgreSQL service. The socket tests deliberately use Channels' in-memory
layer, so this report does not claim Redis pub/sub validation. All data used
in tests was fictional.

## Changes

- Completed the ticket socket protocol with structured message, typing, read,
  and history/sync client events plus structured error events. History is
  ascending by durable message ID and returns results, next_cursor, has_more,
  limit, and after.
- Added an opaque signed, ticket-bound history cursor. PostgreSQL remains the
  durable source; Redis group events are live notifications only, and clients
  explicitly request history after reconnect.
- Revalidate the current Django session and current ticket participation for
  every inbound event and before every outbound group event. Expired/logged-out
  sessions close with 4401; revoked/non-participants receive a structured
  error and close with 4403.
- Added bounded WebSocket input (20 KiB frames, 16 KiB message body bytes,
  4,000 characters), a 60-events-per-minute per-socket budget, one-second
  typing throttling, bounded history pages (maximum 100), and Redis channel
  capacity of 100. These bounds limit amplification; clients recover any
  dropped live event from PostgreSQL history.
- Made client UUID retries safe at the socket boundary. A duplicate with the
  same sender/content receives a unicast duplicate acknowledgement; a UUID
  reused for different sender/content receives message_id_conflict.
- Added ConversationReadReceipt, a durable unique message/reader row, and
  migration desk.0002_conversationreadreceipt. The legacy message read_at
  remains populated on the first receipt for REST compatibility.
- Added ASGI integration coverage for two participants, origin and third-party
  denial, duplicate UUIDs, reconnect/missed history and pagination cursor,
  multiple sessions, persisted read receipts, typing, and permission
  revocation. Documented the frontend-facing event contract.

## Security notes

- Browser WebSockets use session cookies only; URL tokens remain unsupported,
  and exact origin validation occurs before routing.
- Ticket authorization is checked at handshake and again for every operation
  and delivery, including after assignment changes.
- UUID collisions cannot overwrite a persisted message. Read receipts are
  ticket-scoped and cannot be generated by the original sender.
- Error events contain stable codes and safe details, not stack traces or
  message bodies. No message content was logged by this work.
- No commit, push, publication, deployment, private-project access, secret
  access, or customer-data access occurred.
