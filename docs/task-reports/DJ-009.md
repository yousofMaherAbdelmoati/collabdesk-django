# DJ-009 — Django regression and failure tests

Date: 2026-10-24

## Result

PASS — the complete pytest suite passed against the local Compose PostgreSQL
and Redis services using fictional test data only.

## Changes

- Added `tests/service/test_regression_failures.py`, kept separately from
  isolated/unit-style tests and labelled with `service`, `postgres`, and/or
  `redis` markers. Added matching marker documentation in `pytest.ini`.
- Added 20-way, fresh-process PostgreSQL contention tests for ticket
  idempotency, claims, message retries, and report requests. Each contention
  case runs twice (eight 20-way races total); every child is explicitly
  directed to pytest's `test_collabdesk` database, never the Compose
  application database.
- Added a real `channels_redis` WebSocket fan-out, disconnect, reconnect, and
  durable history-recovery test; existing isolated channel tests remain on the
  in-memory layer.
- Added a connection-refusal Redis cache test (unused local port) verifying
  PostgreSQL remains authoritative without stopping the shared Compose Redis
  service.
- Added a real Celery `solo` worker test with two short-lived workers and a
  dedicated Redis database/queue. It submits a duplicate report task, proves
  one persisted attempt, restarts the worker, and proves it completes new
  durable work after restart.
- Added migration-graph integrity coverage after pytest-django applies the
  real migration graph.
- Test-only connection cleanup now sets `CONN_MAX_AGE=0` and closes the ASGI
  thread-sensitive executor connection before test-database teardown. This
  removes PostgreSQL teardown warnings caused by retained asynchronous test
  connections.
- CI now uses `DJANGO_ENV=test` and runs Django system, migration-generation,
  and migration-application checks before pytest. Its PostgreSQL and Redis
  GitHub Actions service containers have health checks and remain required.

Existing regression coverage, executed in the full run, covers authorization
and horizontal privilege escalation, transaction rollback, request replay,
streaming cancellation/limits, report/outbox retry state, duplicate task
handling, and lease-restart recovery.

## Remaining gaps

- No browser/E2E, load, soak, production deployment, or real customer-data
  validation was performed.
- Redis failure is validated as a real connection refusal against an unused
  local port. The shared Compose Redis service was intentionally not stopped,
  so this does not claim an operational failover exercise.
- Celery behavior was validated with local short-lived workers, PostgreSQL,
  and Redis. It does not test external broker clusters, multi-host workers, or
  deployment orchestration.

## Security notes

- All fixtures use fictional usernames, tickets, message bodies, and report
  parameters. Child processes target only the explicit pytest test database.
- The dedicated Celery queue and Redis database isolate the test worker from
  the long-running local demonstration worker.
- Redis remains an optimization/transport in the tests: ticket/report results
  and idempotency guarantees are asserted from PostgreSQL state. The outage
  test confirms cache loss does not remove durable ticket statistics.
- WebSocket tests authenticate with short-lived test sessions and an allowed
  local origin; they verify reconnect recovery from durable message history
  rather than treating Redis broadcasts as durable storage.
