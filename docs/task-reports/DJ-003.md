# DJ-003 — Harden ticket APIs, idempotency and diagnostics

## Result

PASS. The ticket and message API changes were tested locally with SQLite unit
coverage and with the repository's Compose PostgreSQL/Redis stack. The
PostgreSQL run exercised all transaction and 20-worker race cases.

## Changes

- Replaced capped ticket/message lists with signed opaque keyset cursors.
  Ticket cursors use `(created_at, id)` descending and message cursors use
  ascending message IDs, so inserts after a page is issued do not shift its
  continuation. Both endpoints validate cursor and page-size input and return
  `{results, next_cursor}`.
- Retained participant boundaries: customers see their tickets; agents can see
  unassigned open tickets to claim and their assigned tickets; conversation
  access is only customer, assigned agent, or administrator. An agent cannot
  discover or transition an unassigned/resolved ticket through the claim API.
- Added `POST /api/tickets/{id}/status`, supporting the explicit
  `claimed -> resolved` transition. It requires the assigned agent (or admin)
  and `expected_version`; the update condition includes ticket ID, claimed
  status, version, and assigned agent, returning a deterministic conflict for
  stale/concurrent requests.
- Hardened creation idempotency with a locked existing-record read, a retry on
  unique-index contention, persisted completed response replay, deterministic
  different-payload conflicts, and a retryable processing response. Creation,
  outbox event, and stored response remain a single transaction.
- Added a persisted expiry cleanup function and
  `python manage.py cleanup_idempotency_records`. Creation removes an expired
  record while holding its scope lock, so cleanup scheduling delays do not
  prevent a valid post-expiry reuse.
- Added structured JSON application logs for ticket API operational outcomes.
  Events include only operation/outcome (and cleanup count); they exclude
  request bodies, message text, idempotency keys, usernames, user IDs, and
  ticket identifiers.
- Added tests for cursor continuation and invalid cursors, participant access,
  conditional status transitions, expiry cleanup/reuse, rollback on failure,
  diagnostic content exclusion, lost-response replay, payload conflict, and
  PostgreSQL 20-way create/claim contention.

## Security notes

- Cursor tokens are signed and endpoint/type-scoped; message cursors are also
  bound to their ticket. Malformed or cross-list tokens are rejected.
- Conditional database updates, not read-then-write state changes, decide
  claims and resolution across workers.
- Idempotency keys and request content are never emitted in the ticket API's
  structured logs. The new log test uses fictional strings to verify this.
- All test accounts and payloads were fictional local data. No deployment,
  push, publish, commit, private-project access, production service, secret,
  or customer data access occurred.
